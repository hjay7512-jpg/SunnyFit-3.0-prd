# SunnyFit 当前业务与体验对齐审查

日期：2026-10-12。结论：当前 Demo 尚未充分对齐。交易、授权和用量的基础机制已有验证，但页面对象绑定、配置约束、任务回流及原稿还原仍有明确缺口。自动化通过不能作为原业务或用户心智对齐的证明。本轮只审查，未修改原型页面或运行中的商业配置。

后续前端更新现已实施，见 [原稿对齐更新说明](SunnyFit_V3_Frontend_Source_Aligned_Update.md)。内容对象、用量回流、SKU、弹层分类和账户原层级已修正。下文复现结果描述更新前版本，后台发布约束与头像资源验收仍未完成，不应把历史前端问题当作当前仍可复现的缺陷。

## 对齐依据

业务以本会话已确认规则为准：基础训练和记录免费；会员功能权限与 Credits 分开；可预测服务可以纳入包含量；超额付费需要明确确认；新购 Credits 不过期；既有周期承诺和独立获得资产保留；Program 不制造重复课程支付。

个人中心以用户指定的 [Alpha 草稿 221:1177](https://www.figma.com/design/t7g261XYs61EdvYzIZn5YL/V3.0-Alpha?node-id=221-1177) 为设计对照基准。它也已记录在项目初始上下文，不能声称没有原稿。此前其他个人中心节点不得替代它。

Figma 读取现已恢复：通过官方桌面 MCP 读取了用户指定的 `221:1177` Commercialization 画布，确认个人中心和会员用量是画布内的 `249:2123`、`249:2183` 子页面。此前将“未读取到”说成“没有原稿”不成立。原托管插件仍报 Unknown tool，该错误不足以判断 MCP 额度耗尽；[连接恢复与截图证据](SunnyFit_Figma_Connection_Recovery.md)记录当前可用通道。

## 原稿恢复后的界面对照

原个人中心保留身份、Rewards、Badges，并以一个 Membership & Usage 卡片作为商业化入口；Devices & Health、My Orders、Community & Privacy、Settings、Help & Support 等属于既有结构。Demo 应恢复这些原组件，不能用新的会员、钱包、内容目录和报告菜单替换它们。

原 Membership & Usage 二级页集中展示当前方案、用量卡片、Explore Premium，以及 Plan & Benefits、Billing History、Restore Purchase。会员次数与额外 Credits 应在这个既有层级内清晰区分，不先决定拆成两条全新一级导航。当前 Demo 分开的 Membership 与 Usage and Credits 页只能用于验证交易机制，不能当成原 UI 已对齐。

原稿使用浅色底、暖黄色会员卡、红色主要 CTA，以及简洁的列表行。Rewards、Badges 数字的意义保持原业务；AI Coach 百分比和 turns left 则需要根据新包含量规则统一成“剩余 / 总量 + 明确重置日期”，而不是照抄含义未明的 30% 或 Renews next cycle。

这些是对实际原稿的审查结论，本轮没有修改界面。已恢复视觉证据不等于 Demo 已完成还原；正式修正应按原页面层级和状态执行。

## 代码中可确认的条件问题

1. **展示价格与实际购买 SKU 可能不同。** ConsumerScreens.vue:41 优先展示 web_demo SKU；commerceMixin.js:39、137 则购买第一个 Active SKU。多渠道商品只要排列不同，就可能切到另一个渠道、价格或货币。应传递用户看到的确切 SKU，订阅管理沿原购买渠道执行。当前种子只有 web_demo，现有单渠道测试未覆盖此条件。
2. **限额、权限与服务不可用没有分别解释。** CommerceSheets.vue:3 将除权限和包含量耗尽以外的决定都显示为 More Credits，并给出 Add Credits；SERVICE_UNAVAILABLE 没有可消费报价，充值不能解决。包含量耗尽也统一叫 next report，即使实际服务是聊天或分析。应由具体服务和 reason 驱动原弹层文案、动作和恢复路径。
3. **权益摘要忽略 Scope 和授权来源。** ConsumerScreens.vue:46 只按 Item 名称输出 Premium library 等描述。若后台缩小 Scope，用户承诺可能超出实际覆盖。Additional 权益也不能统称为“需要 Premium”；应表述具体可用能力，不将 isMember 替代 Effective Entitlement。
4. **Program 课程选择仍是演示占位。** controller.js:271–273 将第二课程硬编码为 course_premium，原画面仍为 Course2 和固定课程名称。应在原 Program 组件内绑定真实成员和顺序，保留父 Program 授权。已验证的包内访问规则继续保留；不把独立入口另算权益的假设包装成实际会重复收费。
5. **后台 Unlimited 与包含量容易混淆。** 原 Item quota 固定 Unlimited，新增 includedServices 则限制同一服务的包含次数。这是两层不同概念，但当前后台需要明确 Unlimited 描述的是功能访问范围，不代表无限免费生成。无需更换整个后台结构。

## 已有机制可保留的部分

最近独立测试证明：包含量不扣钱包；耗尽不会把旧包含报价悄悄变成付费；超额需要明确确认；失败和超时释放原预留；已保存分析读取不再次计费；Program 在经过验证的父级范围内无需重复兑换；取消续费保留当前周期；套餐切换在周期末模拟生效；同一请求重试不重复发放或扣减。

这些结论限于当前本地模拟实现。恢复购买仅重读演示账户，支付、商店续费和播放器没有生产对接；不可宣称对应生产闭环已完成。

## 尚未定值的业务参数

每月 30 条聊天、两次分析、每周一次报告、次月或次年套餐切换，以及价格和赠送数量仍是 Demo 参数。用户提出周报可预测、可以不走 Credits，并没有批准每周只能生成一次、重置锚点或同周重生成规则。保留“包含服务”方向，将报告周期、重生成和失败恢复按真实业务确认，避免把限制人为加到原体验。

月历订阅与 30 天赠送 Credits 可以存在日期差：是否让新赠送批次随周期结束、按固定有效期，或按月发放，需要同一份承诺。历史批次保持原条件。年付方案的“每月包含量”和“年度付费”应分别说清楚。

## 欧美用户体验的验收重点

这部分是待验证的体验准则，不是已经完成的欧美用户研究。

- 用户应先看懂该操作的价值及访问方式，再看到必要的付费确认。Free、Included、Unlocked、需要独立兑换应对应当前对象，不能只看会员身份。
- 会员页面分别说明下一次付款金额和日期、当前周期、包含服务的重置日期，以及取消的实际结果。年付总价不能只用折算月价替代。
- 用量明确表达剩余多少与何时重置；Credits 显示额外消费的单位和单次费用。无需每次包含内对话都弹付款确认。
- 加购与升级后返回同一任务，保留草稿和内容对象，不自动生成或再次扣费。取消购买也应能继续原来的基础体验。
- 读取已有结果与重新生成明确区分；失败说明本次实际释放的是次数还是 Credits，避免把两者都叫退款。
- Rewards、Badges、旧 Stars 与 Credits 不混为同一种资产；沿个人中心原信息层级呈现，不能用自创资产中心替代。

## 后续修正与验收顺序

Figma 工具读取已恢复。接下来逐项对照 221:1177 画布与既有业务页面，建立“原组件、原动作、真实对象、权限来源、消费来源、返回位置”的对照。随后处理 P0 的对象绑定和配置约束，再修正回流、SKU 与弹层状态；最后在原页面结构内调整字体、间距和长文本。

验收既要有原稿对照，也要有用户从原入口完成任务的证据。构建成功、无横向溢出和直接路由可打开，均不足以单独证明充分对齐。未读到原稿的页面不自行补建；未确认的规则不转为隐含生产政策。
